# Аудит доступности признаков Home Credit

Точка предсказания — момент подачи заявки и принятия кредитного решения.
Для рабочей модели нужно подтвердить, что значение было доступно до решения:
дату события, дату поступления записи и границу расчёта агрегатов.

Организатор описывает датасет как срез на дату решения и отдельно указывает,
что даты преобразованы. Сравнение опубликованных дат помогает выявить
поля для проверки. Оно само по себе не устанавливает момент загрузки или
наличие утечки. [Пояснения Home Credit](https://www.kaggle.com/competitions/home-credit-credit-risk-model-stability/discussion/472866)

## Результат

[Реестр](feature-availability.csv) содержит решение по каждому из 167 полей
`static_0`. Счётчики дат рассчитаны по 1 526 659 размеченным кейсам, до
преобразований из эксперимента с широкой статикой.

| Статус | Полей | Что нужно для использования |
|---|---:|---|
| Кандидат из анкеты | 4 | Сверить с контрактом входной формы. Для типа кредита подтвердить, что это запрошенный продукт. |
| Проверить срез источника | 92 | Подтвердить, что значение или агрегат рассчитаны на срезе до решения. |
| Отложить до проверки дат | 9 | Разобрать преобразование даты и доступность значений в день решения и позже. |
| Проверить момент события | 1 | Дата события предшествует решению во всех заполненных строках. Требуется время загрузки. |
| Исключить | 61 | Оставить за пределами набора до отдельного обоснования. |

У `dtlastpmtallstes_4499206D` 126 627 дат после решения из 549 540
заполненных, у `lastapplicationdate_877D` — 114 236 из 1 221 522,
у `validfrom_1069D` — 54 689 из 151 773. Единственное поле с датами
строго до решения во всех заполненных строках — `datelastinstal40dpd_247D`
(133 818 значений). Даты в день решения не позволяют восстановить порядок
событий внутри дня.

## Источники истории

- **Предыдущие заявки.** Шесть агрегатов используют записи с датой создания
  строго до решения. Для внедрения нужно подтвердить, что поля суммы
  предыдущей заявки отражают версию, доступную на дату среза.
- **Кредитное бюро.** Восемь агрегатов используют дату обновления активного
  или закрытого контракта строго до решения. Отдельно требуется подтвердить
  дату получения выгрузки и что просрочка и суммы относятся к той же версии
  записи.
- **Интерфейс.** Вручную введённое значение доступно приложению к моменту
  расчёта. Это не подтверждает происхождение обучающего признака с тем же
  именем.

Набор на 120 полях остаётся экспериментальным. До использования в выдаче
нужен контракт источника с временными границами для каждого поля.

## Воспроизведение

```sh
uv run --locked python -m credit_scoring.feature_audit
```

## Проверка тестового примера из архива

В `test_base` десять кейсов. Три файла `test_static_0` содержат 30
уникальных ключей, из которых десять совпадают с `test_base`. Проверка
заполненности выполнена только по этим десяти кейсам после соединения по
`case_id`. Все 167 имён признаков присутствуют в тестовой схеме.

- У 156 полей есть хотя бы одно заполненное значение.
- Из 61 поля, исключённого по смыслу, 54 заполнены хотя бы в одном кейсе,
  39 заполнены во всех десяти.
- `credamount_770A` и `disbursedcredamount_1113A` заполнены в 10 из 10,
  `lastapplicationdate_877D` в 10 из 10, `dtlastpmtallstes_4499206D`
  в 5 из 10, `validfrom_1069D` в 0 из 10.

Наличие поля в примере подтверждает, что оно предусмотрено форматом входа
соревнования. Заполненность десяти строк не определяет покрытие скрытого
теста или момент поступления значения в реальную систему. Статусы в
реестре описывают риск использования поля до решения, а не отсутствие
поля в Kaggle.

Типы трёх столбцов отличаются в примере теста. При переносе модели на
соревнование входные типы следует задавать явно по схеме предобработки.
